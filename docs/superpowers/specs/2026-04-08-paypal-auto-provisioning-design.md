# PayPal 自动开通套餐设计

## 1. 背景与目标

当前平台的整体方向已经确定为面向美国开发者提供模型 API 服务，并采用套餐制收费。现阶段需要把 PayPal 支付从“人工确认开通”演进到“支付成功后自动开通套餐”。

本设计的目标是：

- 在 MVP 中支持 PayPal 一次性购买套餐
- 用户完成支付后，由系统自动开通套餐
- 已有有效套餐的用户再次购买时，按顺延叠加处理
- 为后续 PayPal 订阅自动续费保留兼容的数据结构和状态机

本设计不追求在支付完成后一定秒级开通，而是优先保证：

- 不重复发放权益
- 不漏记支付事件
- 发放失败后可补偿
- 后续可平滑扩展到订阅续费

## 2. MVP 范围

### 2.1 包含内容

- 用户在平台内选择套餐并创建本地订单
- 系统调用 PayPal 创建支付单
- 接收并验证 PayPal webhook
- 在支付成功后自动开通套餐
- 有效期内重复购买时顺延套餐到期时间
- 记录支付事件、开通流水与异常状态
- 提供最小可用的补单能力

### 2.2 不包含内容

- PayPal 订阅自动续费的完整上线
- 多支付渠道统一抽象
- 自动退款和退款后自动回收权益
- 争议、拒付、税务等复杂财务流程
- 面向用户的复杂账单中心

## 3. 推荐方案

推荐采用“PayPal Webhook 驱动自动开通”的方案。

整体流程如下：

1. 用户在平台内选择套餐
2. 系统创建本地待支付订单
3. 系统调用 PayPal 创建支付单，并保存 PayPal 订单号
4. 用户在 PayPal 完成付款
5. PayPal 通过 webhook 异步通知平台后端
6. 平台验证事件签名并记录原始事件
7. 平台将支付成功事件映射到本地订单
8. 计费模块执行套餐发放逻辑
9. 平台更新订单状态、套餐状态和权益流水

采用该方案的原因：

- 自动化程度高，用户支付后无需人工确认
- 以支付事件为驱动，后续扩展订阅续费时可复用同一架构
- 能将支付接入与套餐发放解耦，降低后续演进成本

不采用“仅前端回跳触发开通”或“后端轮询 PayPal 状态”的原因：

- 前端回跳不能作为最终可信支付依据
- 轮询实时性差，且后续接入订阅时仍绕不开事件驱动

## 4. 系统架构

建议将能力拆分为 5 个模块。

### 4.1 Checkout / Order

职责：

- 创建本地订单
- 记录用户选择的套餐、金额、币种、周期和订单状态
- 为支付流程生成平台内部唯一订单号
- 作为后续权益发放的核心业务主键

该模块的关键原则是：平台必须以自己的 `order_id` 管理业务流程，不能直接以 PayPal 外部订单号充当唯一业务主键。

### 4.2 PayPal Adapter

职责：

- 调用 PayPal API 创建支付单
- 保存和读取 PayPal 订单号
- 验证 webhook 签名
- 在必要时查询 PayPal 支付详情

该模块只负责“支付事实”的接入与转换，不直接修改用户套餐。

### 4.3 Webhook Handler

职责：

- 接收 PayPal webhook
- 做签名校验
- 记录原始事件
- 对事件进行去重
- 将支付平台事件转换为内部业务事件

该模块不承载复杂权益逻辑，重点是可靠接收、审计和幂等。

### 4.4 Billing / Entitlement

职责：

- 根据订单和账户当前状态发放套餐权益
- 计算新的生效时间和到期时间
- 记录权益变更流水
- 保证套餐发放逻辑幂等

这是“支付成功后自动开通”的唯一业务入口。

### 4.5 Audit / Operations

职责：

- 保存 webhook 原始数据
- 记录处理结果与失败原因
- 支持失败重试与人工补单
- 为后续对账和运营排查提供依据

## 5. 核心数据模型

MVP 至少应包含以下数据实体。

### 5.1 `orders`

用于记录平台内部订单。

建议字段：

- `id`
- `user_id`
- `plan_id`
- `amount`
- `currency`
- `billing_period`
- `status`
- `provider`
- `provider_order_id`
- `paid_at`
- `fulfilled_at`
- `created_at`
- `updated_at`

建议状态至少包括：

- `pending`：已创建，未确认支付
- `paid`：已确认支付成功，但尚未完成权益发放
- `fulfilled`：已完成权益发放
- `failed`：支付或处理失败
- `expired`：订单超时或失效

将 `paid` 与 `fulfilled` 分开是必须的，因为支付成功与权益发放成功是两个独立动作。

### 5.2 `payment_events`

用于保存 PayPal 原始事件与处理状态。

建议字段：

- `provider_event_id`
- `provider`
- `event_type`
- `resource_id`
- `order_id`
- `raw_payload`
- `received_at`
- `processed_at`
- `process_status`
- `error_message`

该表的主要用途：

- webhook 去重
- 事件审计
- 故障重试
- 对账排查

### 5.3 `account_plans`

虽然 MVP 先支持一次性购买，但建议保留账户当前权益表，为后续订阅续费复用。

建议字段：

- `user_id`
- `current_plan_id`
- `status`
- `starts_at`
- `valid_until`
- `updated_at`

建议 `status` 至少支持：

- `inactive`
- `active`
- `expired`
- `suspended`

### 5.4 `entitlement_ledger`

用于记录每次权益变更，是顺延叠加规则的审计基础。

建议字段：

- `id`
- `user_id`
- `order_id`
- `action_type`
- `plan_id`
- `previous_valid_until`
- `new_valid_until`
- `granted_interval`
- `reason`
- `created_at`

该表用于：

- 防止重复发放
- 追踪每次到期时间变更
- 支撑补偿和人工核查

## 6. 核心业务流程

### 6.1 购买与支付

1. 用户选择套餐并提交购买请求
2. 系统创建本地 `pending` 订单
3. 系统调用 PayPal 创建支付单
4. 系统保存 `provider_order_id`
5. 前端跳转或拉起 PayPal 完成支付

### 6.2 支付成功后的自动开通

1. PayPal 发送支付成功 webhook
2. 平台后端验证 webhook 签名
3. 平台将原始事件写入 `payment_events`
4. 平台根据外部订单号关联本地订单
5. 平台校验订单金额、币种和状态
6. 若校验通过，则将订单状态更新为 `paid`
7. `Billing / Entitlement` 执行权益发放
8. 平台写入 `entitlement_ledger`
9. 平台更新 `account_plans`
10. 平台将订单状态更新为 `fulfilled`

### 6.3 顺延叠加规则

重复购买时按以下规则计算套餐到期时间：

- 如果账户当前 `valid_until` 晚于当前时间，则从原 `valid_until` 继续顺延一个套餐周期
- 如果账户当前已过期或没有有效套餐，则从当前时间开始计算新的套餐周期

示例：

- 用户当前有效期到 `2026-05-01`，在 `2026-04-20` 再购买一个月套餐，则新到期时间变为 `2026-06-01`
- 用户套餐已于 `2026-04-01` 过期，在 `2026-04-08` 购买一个月套餐，则新到期时间变为 `2026-05-08`

## 7. 幂等与异常处理

自动开通链路必须优先保证可靠性。MVP 至少实现三层幂等保护。

### 7.1 事件去重

以 `provider_event_id` 为唯一标识。若同一 PayPal webhook 被重复投递，系统只处理一次。

### 7.2 订单幂等

若订单已经是 `fulfilled`，后续重复事件不得再次触发权益发放。

### 7.3 权益发放幂等

建议对 `entitlement_ledger` 中的 `order_id + action_type` 建立唯一约束，防止同一笔订单被顺延两次。

### 7.4 异常场景

MVP 至少要覆盖以下情况：

- webhook 验签失败：拒绝处理，记录日志
- 收到支付成功事件但查不到本地订单：标记异常并等待排查
- 金额或币种与本地订单不一致：不发放套餐，进入异常状态
- 支付确认成功但权益发放失败：订单停留在 `paid`，等待重试
- 用户前端已看到支付成功页，但 webhook 尚未到达：前端展示“支付处理中”

### 7.5 补单机制

MVP 至少提供一种补偿方式：

- 管理后台支持按订单重新执行 fulfill

或者：

- 后台定时任务自动扫描 `paid but not fulfilled` 订单并重试

两者任选其一即可，优先保证出现故障后可补发。

## 8. 面向后续订阅的兼容设计

虽然 MVP 暂不实现订阅自动续费，但本设计要求当前数据结构对后续扩展友好。

需要预留的扩展点：

- `account_plans` 作为统一账户权益表，不与“一次性订单”强耦合
- `payment_events` 保留通道、事件类型和原始资源标识，便于后续接入订阅事件
- `Billing / Entitlement` 只接收“发放一个周期权益”的业务输入，不依赖具体支付形态
- `orders` 状态机保留“已支付未发放”的中间态，方便复用到续费场景

后续接入订阅时，新增的主要是：

- 订阅创建事件处理
- 续费成功事件处理
- 续费失败与取消订阅事件处理

而不是推翻当前一次性购买的主链路。

## 9. 测试策略

MVP 至少应覆盖以下测试。

### 9.1 单元测试

重点验证套餐顺延规则：

- 无有效套餐时购买，从当前时间开始生效
- 有效期内购买，从原到期时间顺延
- 重复执行同一订单，不会重复发放

### 9.2 集成测试

重点验证 webhook 到发放的主链路：

- 合法事件可将订单推进到 `fulfilled`
- 重复事件不会重复开通
- 金额不一致时进入异常状态
- 发放失败时订单保留在 `paid`

### 9.3 回归测试

至少覆盖以下边界：

- 套餐过期后再次购买
- 管理员手工补发
- 已开通订单重复重试

## 10. 落地结论

本次设计确认以下实现方向：

- MVP 支持 PayPal 一次性购买套餐
- 支付完成后通过 PayPal webhook 自动开通套餐
- 有效期内重复购买按顺延叠加处理
- 订单状态必须区分 `paid` 与 `fulfilled`
- 必须落地事件审计、幂等保护和最小补单能力
- 当前设计需兼容未来的订阅自动续费扩展

该设计聚焦于“支付成功后自动、安全、可补偿地开通套餐”，不在 MVP 内引入复杂订阅、退款或财务系统能力。
