# 模型服务 API 平台设计

## 1. 项目概述

本项目目标是建设一个面向美国独立开发者的模型服务 API 产品。产品不训练自有模型，而是代理第三方模型服务，并以更低价格提供兼容 OpenAI API 和 Anthropic API 的调用体验。

第一阶段商业定位：

- 面向美国独立开发者和小团队
- 主打低价代码模型替代方案
- 对外提供 OpenAI 兼容 API 和 Anthropic 兼容 API
- 上游先接入 Minimax、Kimi、GLM 等中国模型服务提供商
- 收费方式采用多档套餐，套餐内包含额度，超额后暂停调用
- MVP 先采用 PayPal 自动开通的一次性购买模式，后续扩展到订阅自动续费

## 2. MVP 范围

### 2.1 MVP 包含内容

- 对外官网
- 用户注册与登录
- 用户控制台
- API Key 管理
- OpenAI 兼容 API 网关
- Anthropic 兼容 API 网关
- 请求 usage 采集
- 套餐与额度管理
- PayPal 自动开通的一次性购买
- 管理后台

### 2.2 MVP 不包含内容

- 自研或训练模型
- 企业销售能力
- 团队/组织权限体系
- 请求级日志查询界面
- API Key 维度 usage 展示
- 模型权限配置
- 用户侧模型路由管理
- 自动化订阅扣费
- 复杂 BI、财务分析或风控系统

## 3. 产品定位

产品对外核心价值主张：

- 比头部国际模型服务更低价
- 兼容现有 OpenAI / Anthropic 客户端接入方式
- 更适合以代码调用为主的开发者集成场景

产品不是“最全模型聚合平台”，而是“低价代码模型 API 平台”。第一版不强调上游数量，而强调：

- 接入简单
- 价格透明
- 兼容性明确
- 套餐与额度规则清晰

## 4. 系统模块划分

建议拆分为 5 个模块。

### 4.1 官网站点

职责：

- 对外展示产品价值
- 展示价格套餐
- 展示兼容性与文档入口
- 承接注册与登录转化

不负责复杂业务逻辑。

### 4.2 用户控制台

职责：

- 展示账户状态
- 展示当前套餐状态
- 展示账户总 usage 汇总
- 管理 API Key
- 发起购买或升级流程
- 展示付款状态

第一版仅展示账户级汇总，不展示请求明细、模型维度或 API Key 维度 usage。

### 4.3 API 代理网关

职责：

- 接收 OpenAI 兼容请求
- 接收 Anthropic 兼容请求
- 校验 API Key
- 校验账户套餐状态和额度状态
- 转发请求到上游模型服务
- 处理兼容响应
- 记录 usage 与计费事件

### 4.4 计费与订阅核心

职责：

- 管理套餐定义
- 管理账户套餐状态
- 发放和扣减额度
- 记录账单周期
- 判断是否超额
- 决定是否暂停调用
- 接收支付成功事件并自动发放权益

### 4.5 管理后台

职责：

- 配置网关侧模型路由与上游凭证
- 管理套餐内容
- 处理异常订单与补单
- 调整账户套餐与状态
- 查看运营所需的账户、订单、usage 汇总

## 5. 核心数据流

### 5.1 注册与开通

1. 用户访问官网并注册账户
2. 用户进入控制台选择套餐
3. 系统创建本地订单并调用 PayPal 创建支付单
4. 用户完成 PayPal 付款
5. PayPal 通过 webhook 通知平台支付成功
6. 系统自动更新账户套餐状态，并发放当期额度
7. 用户创建 API Key 并开始调用

### 5.2 API 调用与计费

1. 用户使用 API Key 调用 OpenAI 兼容接口或 Anthropic 兼容接口
2. 网关校验 API Key、账户状态、套餐状态与剩余额度
3. 若可调用，则按预设路由配置转发到上游模型
4. 网关接收响应并返回给客户端
5. 网关记录 usage 事件和计费事件
6. 计费系统更新账户当期累计 usage
7. 若达到套餐额度上限，则将账户切换为暂停调用状态

## 6. API 网关设计

### 6.1 对外能力

第一版网关必须提供：

- OpenAI 兼容 API
- Anthropic 兼容 API

用户创建的 API Key 默认可以调用当前平台开放的所有模型。

第一版不做：

- API Key 级模型权限控制
- 用户侧模型路由配置
- 用户侧模型管理后台

### 6.2 内部执行流水线

两套兼容接口在内部统一到同一条执行链路：

1. API Key 鉴权
2. 账户状态检查
3. 套餐状态与额度检查
4. 请求转发
5. 响应兼容处理
6. usage 采集
7. 计费事件入库

### 6.3 路由策略

第一版不要求建立完整的模型目录系统。模型与上游路由关系由你在网关侧手动配置。

该配置至少要支持：

- 请求模型名
- 上游服务提供商
- 上游真实模型标识
- 所用上游凭证
- 所属兼容协议
- 启用/停用状态

这些配置先作为内部运营配置存在，不需要第一版做成用户可见或可配置能力。

### 6.4 usage 采集要求

`usage` 采集是第一版硬要求，必须以请求级事件形式记录，不能只保留汇总值。

建议至少采集以下字段：

- 账户 ID
- API Key ID
- 协议类型
- 请求模型名
- 上游供应商
- 输入 token
- 输出 token
- 总 token
- 请求时间
- 请求结果状态
- 错误类型
- 请求耗时
- 内部成本信息
- 账单周期归属

虽然用户第一版只看到账户级汇总，但内部必须保存更细粒度数据，用于：

- 对账
- 补账
- 超额判断
- 成本核算
- 故障排查
- 后续扩展更细的报表能力

## 7. 套餐、计费与支付设计

### 7.1 套餐结构

第一版采用多档套餐。MVP 先落地为一次性购买并自动开通，每个账户同一时刻只有一个有效套餐；后续再在同一套数据结构上扩展订阅自动续费。

每个套餐至少包含：

- 月费
- 计费周期
- 套餐内额度
- 超额规则
- 速率限制
- 套餐状态说明

### 7.2 额度规则

产品规则已确认：

- 套餐内提供固定额度
- 超过套餐额度后暂停调用
- 不允许继续透支调用

这样可以降低第一版的资金风险和人工对账压力。

### 7.3 支付方式

第一版支付采用 PayPal 自动开通的一次性购买模式：

- 用户在网站或控制台发起购买
- 系统创建本地订单并拉起 PayPal 支付
- 用户通过 PayPal 完成付款
- PayPal 通过 webhook 异步通知平台
- 系统验证支付结果后自动激活对应套餐
- 若自动开通失败，则进入异常订单处理或补单流程

### 7.4 系统状态设计

即使采用自动开通，账务状态也必须是系统化的。建议至少具备：

- 待付款
- 已支付待发放
- 已激活
- 已过期
- 已暂停
- 已停用

### 7.5 未来演进要求

虽然第一版先使用 PayPal 自动开通的一次性购买，但数据结构和状态机必须支持未来扩展到订阅自动续费。后续若切换到 Stripe 等方式，应尽量只替换付款事件来源，而不重做套餐、账单和额度系统。

## 8. 官网与控制台设计

### 8.1 官网信息架构

第一版官网建议包含：

- 首页
- 价格页
- API 兼容说明页
- 模型列表页
- 文档页
- 登录/注册入口

首页重点表达：

- 为什么便宜
- 如何兼容 OpenAI / Anthropic
- 适合哪些开发者

价格页需要明确说明：

- 套餐内容
- 套餐额度
- 超额后暂停调用
- 当前购买流程为 PayPal 自动开通

文档页重点提供：

- OpenAI 兼容接入示例
- Anthropic 兼容接入示例
- 认证方式说明
- 基本错误说明

### 8.2 控制台能力

第一版控制台建议包含：

- 账户资料
- 当前套餐状态
- 当前周期账户总 usage
- API Key 列表与创建/停用
- 购买/升级入口
- 付款状态

第一版不提供：

- API Key 维度 usage 展示
- 请求日志明细
- 模型维度统计图
- 团队协作功能

## 9. 错误处理与风控

### 9.1 账户与套餐错误

网关需要稳定返回以下类型错误：

- API Key 无效
- 账户无有效套餐
- 套餐已过期
- 套餐额度已耗尽
- 账户被停用

当额度耗尽时，网关必须立即阻断请求，而不是继续转发到上游。

### 9.2 上游错误

第一版至少要能区分并记录：

- 上游超时
- 上游认证失败
- 模型不可用
- 上游限流
- 响应格式异常

即使暂时不做自动故障切换，也要保留标准化错误记录，便于排查和后续优化。

### 9.3 风控基础能力

第一版至少要具备：

- 基本速率限制
- 异常调用监控
- 手动封禁 API Key
- 手动封禁账户

## 10. 测试重点

第一版最重要的测试范围：

- OpenAI 兼容接口测试
- Anthropic 兼容接口测试
- usage 采集正确性测试
- 套餐额度耗尽后的阻断测试
- 账单周期与套餐状态测试

测试优先级高于复杂视觉或非关键后台能力。产品成立的前提是：

- 用户能稳定调用
- usage 算得准
- 套餐状态切换正确
- 超额后能准确暂停调用

## 11. 分阶段落地建议

### 阶段 1

- API 网关最小闭环
- usage 事件落库
- 账户、套餐、API Key 基础模型
- PayPal 自动开通的一次性购买

### 阶段 2

- 官网与开发者文档
- 用户控制台
- 套餐购买与异常订单处理流程

### 阶段 3

- 管理后台增强
- 运营报表
- 订阅自动续费能力

## 12. 当前确认结论

- 面向美国独立开发者
- 商业模式为自有转售
- 第一版整体设计覆盖官网、控制台、网关、套餐计费与管理后台
- 提供 OpenAI 兼容 API 和 Anthropic 兼容 API
- 上游先接入 Minimax / Kimi / GLM 等模型服务
- 用户可创建多个 API Key
- API Key 默认可调用所有已开放模型
- 第一版 usage 只对用户展示账户级汇总
- 第一版网关必须进行完整 usage 采集
- 模型与路由配置由网关内部手动维护
- 套餐采用多档套餐
- 超额后暂停调用
- MVP 支付先采用 PayPal 自动开通的一次性购买
- 系统必须为未来订阅自动续费升级预留结构
