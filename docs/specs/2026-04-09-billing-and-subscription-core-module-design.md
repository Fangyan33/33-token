# 计费与订阅核心模块设计

> 本文是 [`2026-03-27-model-api-platform-design.md`](./2026-03-27-model-api-platform-design.md) 的模块细化文档之一。
> 本文只描述计费与订阅核心模块，不重复总设计中的项目背景、商业定位与整体 MVP 范围。
> 与 API 网关之间的接口边界与时序细化，见 [`2026-04-09-gateway-billing-interaction-design.md`](./2026-04-09-gateway-billing-interaction-design.md)。

## 1. 模块目标与非目标

### 1.1 模块目标

计费与订阅核心是平台的业务状态中心，承担以下目标：

- 管理套餐定义
- 管理账户套餐状态与账单周期
- 发放和扣减额度
- 接收支付成功事件并自动发放权益
- 判断是否超额并输出暂停调用状态
- 为网关、控制台和管理后台提供统一账务结论

### 1.2 模块非目标

计费与订阅核心不承担以下职责：

- 不负责直接处理外部模型 API 请求
- 不负责渲染前端页面
- 不负责持有上游模型路由配置
- 不负责成为支付平台原始回调展示层

## 2. 职责边界与上下游依赖

### 2.1 职责边界

计费与订阅核心负责业务状态真相，不负责对外请求执行。

该模块负责：

- 套餐定义与状态管理
- 订单状态管理
- 支付事件接入后的业务状态更新
- 账户权益发放
- 周期内额度汇总与暂停规则

该模块不应绕过边界去做：

- 上游模型调用
- 页面状态渲染
- 网关协议处理

### 2.2 上下游依赖

计费与订阅核心依赖：

- 支付集成层：提供 PayPal 等支付平台的标准化事件
- usage 事件来源：主要来自 API 网关
- 管理后台：提供人工补单、人工调整入口
- 用户控制台：消费账务状态进行展示
- API 代理网关：消费账户可调用性判断结果

## 3. 核心数据对象

建议至少定义以下核心数据对象。

### 3.1 套餐定义

用于描述“卖什么”，至少包含：

- 套餐标识
- 套餐名称
- 价格
- 计费周期
- 套餐内额度
- 超额规则
- 速率限制
- 套餐状态说明
- 是否启用

### 3.2 账户权益状态

用于描述“账户当前拥有什么”，至少包含：

- 账户 ID
- 当前生效套餐
- 当前账单周期起止时间
- 当前周期已使用额度
- 当前周期剩余额度
- 当前权益状态
- 是否暂停调用

### 3.3 订单

用于描述一次购买过程，至少包含：

- 订单 ID
- 账户 ID
- 套餐标识
- 支付金额
- 支付方式
- 订单状态
- 创建时间
- 完成时间

### 3.4 支付事件

用于描述第三方支付平台回传的标准化支付事实，至少包含：

- 事件 ID
- 外部支付单号
- 事件类型
- 订单关联信息
- 支付结果
- 支付时间
- 原始来源标识

### 3.5 周期汇总

用于承接请求级 usage 的周期累计结果，至少包含：

- 账户 ID
- 账单周期
- 输入 token 汇总
- 输出 token 汇总
- 总 token 汇总
- 当前已消耗额度
- 当前剩余额度
- 当前可调用状态
- 最近更新时间

## 4. 状态机设计

### 4.1 订单状态

订单状态建议至少包括：

- 待付款
- 已支付待发放
- 已完成
- 已失败
- 已取消
- 需人工处理

设计原则：

- 支付成功不等于权益已发放
- 需要保留“已支付待发放”状态吸收异步处理延迟
- 重复回调或异常金额应进入幂等校验或人工处理路径

### 4.2 账户权益状态

账户权益状态建议至少包括：

- 无有效套餐
- 已激活
- 已暂停
- 已过期
- 已停用

状态切换需与网关阻断逻辑保持一致。

## 5. 核心规则设计

### 5.1 套餐规则

第一版采用多档套餐，同一账户同一时刻只有一个有效套餐。

第一版规则明确为：

- 套餐内提供固定额度
- 超过额度后暂停调用
- 不允许继续透支调用

### 5.2 周期规则

每个账户的权益必须归属到明确账单周期。

系统需要支持：

- 周期开始
- 周期内累计
- 周期结束
- 过期后状态转换

虽然第一版先采用一次性购买自动开通，但数据结构必须为未来订阅续费保留兼容空间。

### 5.3 扣减规则

请求级 usage 事件进入后，应映射到对应账单周期进行累计。

建议区分两层数据：

- 原始 usage 事件：用于审计、补账和排查
- 周期汇总结果：用于高频读取和快速判定

第一版中，这两层数据都以 PostgreSQL 为准，不引入 Redis 作为额度判定前提。

其中：

- 原始 usage 事件用于留存完整请求事实
- 周期汇总结果作为账户当前可调用状态与剩余额度的实时读模型

API 网关在请求转发前直接读取周期汇总结果，而不是扫描原始事件。

### 5.4 暂停规则

当周期内累计消耗达到套餐上限时，账户应被标记为暂停调用。

暂停应直接影响：

- 网关放行判断
- 控制台状态展示
- 管理后台查询结果

### 5.5 MVP 校验策略

第一版采用“转发前查汇总、请求后扣减”的策略，不做请求级额度预占。

这意味着：

- 账户在转发前只要仍处于可调用状态且剩余额度大于 0，就允许请求进入
- 请求执行完成后按真实 usage 更新周期汇总
- 若该次请求使额度被耗尽，则从下一次请求开始阻断

该策略接受“最后一个请求可能把额度打穿一点点”的边界，以降低 MVP 实现复杂度。

## 6. 支付事件接入设计

### 6.1 当前阶段

第一版使用 PayPal 自动开通的一次性购买模式。

推荐边界是：

- 支付集成层负责验签和标准化支付事实
- 计费核心只消费标准化支付事件并更新订单与权益状态

### 6.2 未来扩展

为了支持未来订阅自动续费或替换支付方式，计费核心不应绑定某一支付平台专有字段和流程。

未来若接入 Stripe 或新增订阅续费，原则上只替换支付事件来源，而不重做套餐、订单和权益系统。

## 7. 异常处理与幂等性

该模块至少处理以下异常：

- 重复 webhook
- 支付成功但权益未发放
- 订单金额与套餐不一致
- 套餐已下架但旧订单回调仍到达
- usage 重复入账
- 汇总延迟
- 账户已被人工停用后再次收到支付成功事件

处理原则：

- 所有支付事件处理必须幂等
- 权益发放必须可重试
- 异常订单必须可人工修正
- 原始事实与修正动作都必须可审计

## 8. 对外输出能力

计费与订阅核心建议提供以下统一能力：

- 查询账户当前权益状态
- 查询当前周期汇总
- 判断账户是否允许调用
- 创建订单
- 应用支付事件
- 执行人工补发或状态修正
- 查询订单状态

这些能力供控制台、网关和后台统一消费，避免业务规则散落在多个模块中。

## 9. 权限与安全约束

计费与订阅核心属于高敏感模块，至少满足：

- 只有受控内部服务和后台接口可写入
- 关键状态变更应保留审计记录
- 支付事件处理需有来源验证和幂等保护
- 人工修正动作必须具备操作留痕

## 10. MVP 范围内与范围外

### 10.1 MVP 范围内

- 多档套餐定义
- 一次性购买订单
- PayPal 支付成功后自动开通
- 周期内额度累计
- 超额后暂停调用
- 订单状态查询
- 异常订单人工处理入口

### 10.2 MVP 范围外

- 自动续费订阅
- 复杂财务分析
- 多币种结算
- 企业合同账单
- 信用额度和后付费体系

## 11. 测试与验收重点

计费与订阅核心至少验证：

- 首次购买后套餐激活正确
- 重复支付事件幂等
- 周期内 usage 累计正确
- 达到额度上限后账户被暂停
- 周期汇总可作为网关转发前的实时判定依据
- 额度被最后一次请求耗尽后，后续请求会被阻断
- 订单状态与权益状态联动正确
- 套餐过期与状态转换正确
- 人工补单和人工恢复路径可用
